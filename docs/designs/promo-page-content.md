## Problem Statement
The homework requires a promo page for plant_care on GitHub Pages: what it is, who it's for, how to try it. The README's "demo" section is written for someone already reading the repo's source, not for a stranger landing on a page. No dedicated promo content exists yet.

## What Makes This Cool
Two things carry the page:
1. **Real Google Calendar integration** — watering reminders aren't a bespoke in-app notification system; they're actual all-day Google Tasks the user already sees on their phone. Ticking one off there (not just in the app) resets the countdown. This is the "whoa" — no new app to check, no new habit to build.
2. **Personalized watering estimate** — three quick questions at add time (light, warmth, pot material) plus post-watering feedback ("soil was still wet" / "leaf was drooping" / "right on time") tune the interval for that specific plant, instead of one fixed number for every Monstera that ever existed.

## Constraints
- Static page, GitHub Pages, public repo (esst-prog2/plant_care) — nothing personal goes in the published folder.
- plant_care itself only runs locally right now (`python run.py`); there is no hosted live demo to link to. "How to try it" means clone + run locally, not a live URL.
- Course deadline; content needs to be ready before the look is shaped with Impeccable (separate homework step).

## Premises
1. The page presents plant_care as a real product, with a short course-context note, not as dry documentation. **Agreed.**
2. The headline message is the calendar integration + the personalized watering estimate; toxicity data, groups and cover photos are supporting mentions only, not headline material. **Agreed.**
3. "How to try it" is a clone-and-run walkthrough, not a live link, since the app only runs locally today. **Agreed.**
4. The differentiating line is "a real calendar integration, not another app to check" — positioned against a general calendar-only, next to known names like Planta or Greg which *do* add another app to check. **Agreed.**

## Approaches Considered
### Approach A: Minimal single-scroller
Hero line + 3 feature blocks (calendar, personalized watering, safety data) + a "How to try it" section. Effort: S. Fewest files, fastest to ship, but thin — no visual proof the app actually works.

### Approach B: Structured page with a real-screenshot gallery
Scroll-anchored sections (what it is → who it's for → how it works, with real UI screenshots already captured this session → how to try it). Effort: M. Backs up every claim with an actual picture of the running app instead of describing it in prose alone.

*(A third, more playful approach — the page itself styled as an oversized "plant card" in the app's own visual language — was considered but not chosen; B's screenshot-led structure was preferred as the more direct way to prove the app is real and working.)*

## Recommended Approach
**Approach B**, with one cut from the original pitch: no dedicated "why not another app" comparison callout. The user explicitly asked for this to be dropped — the calendar-integration differentiator still comes through in the feature description itself, just not as its own competitive-comparison section.

Final content structure for Approach B:
1. **Hero** — one line stating what plant_care is + who it's for, course-context note in small print.
2. **What it is** — short paragraph, framed as a real tool, not an assignment writeup.
3. **How it works** — the two headline features (calendar integration, personalized watering), each with a real screenshot. Toxicity/humidity/propagation data, groups with cover photos, and photo upload get one supporting line each, no screenshots required.
4. **How to try it** — clone, create a venv, install requirements, run `python run.py`, open localhost:8000. No live link.
5. Footer: link to the GitHub repo, one line noting this is a semester project.
