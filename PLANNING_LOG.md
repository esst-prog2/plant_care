# Planning Log

- 2026-09-22 — Adopted OpenSpec folder conventions: `openspec/config.yaml` holds settings and is left at its defaults; `openspec/specs/` is the source of truth for what the program currently does; `openspec/changes/` holds work-in-progress proposals not yet merged into specs. Decided by user.
- 2026-09-23 — First OpenSpec change named `add-plant-care-mvp`, split into four capabilities: `plant-collection`, `plant-care-data`, `watering-tracker`, `email-notifications`. Decided by Claude (user asked for a first change based on the README scope).
- 2026-09-23 — Daily summary email defaults to 08:00 local time, is skipped when nothing is due, and a watering confirmation email is sent when "Watered" is pressed. Decided by Claude (proposed in spec, user to review).
- 2026-09-23 — Watering interval defaults to 7 days when the data source gives no usable value; countdown is derived from the last-watered date rather than decremented by a job. Decided by Claude (proposed in design, user to review).
- 2026-09-23 — Assumed a single user with no login, and a grid that wraps to extra rows after the first 3×2 (six) plants. Decided by Claude (assumptions, user to review).
- 2026-09-23 — Tech stack and plant-data API left undecided on purpose; design.md lists options A/B/C (recommended: A, Python FastAPI + HTMX + SQLite) and candidate APIs (Perenual, Trefle, OpenPlantbook). Decided by user (they asked for options rather than a choice).
- 2026-09-23 — The homepage keeps a fixed 3×2 grid (six cards per page) and larger collections are paged with previous/next controls, instead of wrapping onto extra rows. Decided by user.
- 2026-09-23 — Dropped the watering confirmation email; the daily summary is the only email the app sends (this supersedes the confirmation-email part of the 08:00 entry above). Decided by user.
- 2026-09-23 — Tech stack chosen: Option A, Python with FastAPI, Jinja2 + HTMX and SQLite (supersedes the "stack undecided" entry above). Decided by user (on Claude's recommendation).
- 2026-09-23 — Rule: only free solutions; no payment method attached to any service, so no cost can arise. Decided by user.
- 2026-09-23 — Daily email starts local (computer must be on; a missed email is sent at next startup); moving the daily send to a free cloud scheduler and cloud database is a later step only if the local approach is not enough. The daily send is a standalone command and database access sits behind one thin module to keep that switch cheap. Decided by user (design wording by Claude).
- 2026-09-23 — Plant API: Perenual's free plan (100 requests/day, species 1-3000, has photo, sunlight and watering) is the only candidate that fits; Trefle rejected (care data almost empty), Open Plantbook rejected (sensor values, no watering interval in days). Not final until the user creates a free key and confirms no card is asked (task 1.2). Decided by Claude (proposal, awaiting user).
- 2026-09-23 — Built-in offline plant list has 12 common houseplants with watering intervals of 7, 14 or 21 days taken from general knowledge, all shown with one placeholder illustration instead of photos. Decided by Claude.
- 2026-09-23 — Interval from the API: lower bound of a day range (e.g. "7-10" becomes 7); wording maps to Frequent=3, Average=7, Minimum=14 days, anything else 7. Decided by Claude.
- 2026-09-23 — Daily email is checked every minute while the app runs; a failed send is retried every 15 minutes until the end of the day. Decided by Claude.
- 2026-09-24 — Watering reminders will come from Google Calendar events instead of email, because the computer is not on every day but the phone almost always has internet and the Google Calendar app. Email sending is dropped (supersedes the daily email entries above). The existing change add-plant-care-mvp is revised in place rather than opening a follow-up change, since email was never released. Decided by user (in-place revision chosen by Claude).
- 2026-09-24 — Reminder model: one all-day Google Task per plant (Option A), due on the next watering date; ticking it off on the phone sets the last-watered date to the completion date, so the countdown counts from the tick and not from when the computer starts. Decided by user (task-based design proposed by Claude).
- 2026-09-24 — The capability `email-notifications` is replaced by `calendar-reminders` (new spec created, old spec deleted). Decided by user.
- 2026-09-24 — Sync rules: tasks live in a dedicated Google Tasks list named `plant_care`; the app syncs at start, every 10 minutes while running and after add/watered/remove; if the phone tick and the in-app "Watered" disagree, the later date wins; deleted or moved to-dos are restored by the app. Decided by Claude (proposal in design.md, user to review).
- 2026-09-24 — A Google service account is rejected because it cannot reach a personal Tasks list. Google access method stays open between OAuth "In production" and an Apps Script web app, decided by two checks in task 6.1 (does creating a Google Cloud project ask for a payment method; does an all-day to-do notify on the phone). Decided by Claude (finding); choice pending with user.
- 2026-09-24 — Option A (all-day Google Tasks only) stays as the reminder model even if the phone does not notify on all-day to-dos; the phone check in task 6.1 is informational only and a timed event (Option B) is not planned. Decided by user.
- 2026-09-24 — Each plant always has two open to-dos in Google (its next two watering dates, one interval apart), so a reminder is still waiting if the computer stays off after a tick; the app realigns both after any watering and deletes a third one. Decided by user (implementation wording by Claude).
- 2026-09-24 — Google Cloud asked for a payment method when the user tried to create a project, so the OAuth route is rejected and Google access will be a small Apps Script web app in the user's own Google account, protected by a shared secret. Whether Apps Script itself asks for a payment method is still to be checked (task 6.1); if it does, Google reminders are dropped. Decided by user (finding) and Claude (choice following the rule "only free solutions").
- 2026-09-24 — Plant data API: Perenual, because its free plan asks for no payment details (checked by the user). Still to verify with a real request that Monstera and Pilea are within the free species range and return photo, light and watering (task 1.2). Decided by Claude (proposal), confirmed by the user's payment check.
- 2026-09-24 — Apps Script check passed: adding the Google Tasks API service and deploying a test web app asked for no payment method, so Google reminders go ahead through an Apps Script web app. Decided by user (check result).
- 2026-09-24 — Implementation choices for the Google sync: to-dos are recognised by a marker with the plant id in their notes, so no to-do ids are stored locally; to-dos the app completes itself are marked "recorded" so they are not read back as a phone tick; completed to-dos are left in the list as a history. Decided by Claude (design.md and tasks.md updated to match).
- 2026-09-24 — Tested Perenual with the real free key: search works, but Monstera and Pilea (ids 5257, 6068 and others, beyond the free species 1-3000) return only "Upgrade Plans" placeholders for photo, light and watering, and their detail calls answer HTTP 429 "Please Upgrade Plan"; searches for 16 other common houseplants gave no usable data either, and even free-range species (firs, yarrow, bottlebrush) came back with empty watering and sunlight. So Perenual's free plan cannot supply the care data the README needs; the earlier choice of Perenual is withdrawn and the replacement is pending the user's decision. Finding by Claude.
- 2026-09-24 — Plant data sources: light and watering interval come from a bundled list of about 40 common houseplants (values from general knowledge, so approximate); the photo and a short description are fetched from Wikipedia's free page-summary service when a plant is added, with the placeholder illustration when Wikipedia cannot be reached. Perenual is dropped and its code removed. Decided by user (from options offered by Claude).
- 2026-09-24 — Wikipedia rejected requests without contact details (HTTP 403, robot policy), so the requests send a User-Agent naming the project repository https://github.com/esst-prog2/plant_care; no personal address is sent. Decided by user.
